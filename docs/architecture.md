# Architecture

Command Table uses one shared, validated game domain with a local IndexedDB controller and a server-backed room controller. The frontend is React/TypeScript, Zustand, Radix Dialog, and CSS; Fastify serves the production app and WebSocket API. Exact dependency versions are in `package-lock.json`; Node 24 is the deployment target.

The original `mtg-util` storage keys, database filename, export-format identifier, protocol headers, and Compose service/volume names remain stable. Renaming the app does not create a new database or invalidate existing saves, shared memberships, or exported games.

## Boundaries

| Area             | Files                                              | Responsibility                                                                          |
| ---------------- | -------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Domain           | `src/shared/schema.ts`, `game.ts`, `random.ts`     | Bounded contracts, referential checks, pure reducer, injected time/IDs/random results   |
| Local controller | `src/client/app/store.ts`, `storage/repository.ts` | Hydration, optimistic preview, serial transactions, leases, recovery, archives          |
| Room controller  | `src/client/adapters/room.ts`                      | Guest renewal, durable pending envelopes, revisions, reconnect, authoritative snapshots |
| Interface        | `src/client/features/`, `components/`, `styles/`   | Mobile board/sheets, cancelable hold input, accessibility, utilities, local preferences |
| Server           | `src/server/app.ts`, `service.ts`, `traffic.ts`    | HTTP/WS validation, authorization, transactional commands, retention, broadcasting      |
| Card lookup      | `src/server/cards.ts`                              | Constrained Scryfall endpoints, serialized upstream queue and bounded cache             |
| Database/config  | `src/server/database.ts`, `config.ts`              | SQLite migration and pragmas, explicit origin/security configuration                    |
| Operations       | `src/server/operations.ts`                         | Private diagnostics and scheduled verified backups                                      |

Core game tracking needs no accounts, analytics, hardware fingerprints or external cloud services. Optional card search, artwork, readable card details and rulings use Scryfall through constrained server endpoints and bounded caches; unavailable card data does not block counters. Names and commander labels are rendered as text. All players, commanders, matches, members, and operations have independent stable IDs.

Appearance is browser-local: `theme` selects `system`, `light` or `dark`; `colorTheme` selects a palette; `accentColor` selects one of eight accents; and `tableFinish` selects one of eight materials. Older profiles default to system mode, Classic, Gold and Astral silk; existing finish IDs remain valid. The `tabletop` finish now displays Dragonfire in place of velvet, and `obsidian` displays Stormglass lightning in place of volcanic glass. Gold keeps the historical `theme` accent ID and uses fixed gold shades across all palettes; Red keeps the historical `gold` ID. This preserves saved profiles and first-paint caches while removing the redundant Theme default option. Palette seeds in `appearance.css` drive the app and its Settings previews, with separate light/dark accent shades for readable contrast. `table-finishes.css` combines static gradients and seven self-hosted SVGs into matching table, player-panel and picker materials; commander-art panels retain their artwork treatment. The SVGs are precached for offline use. Player colors, card artwork and dice materials remain independent. IndexedDB remains authoritative; validated localStorage mirrors let the external `appearance.js` bootstrap apply the choices before hydration. The mounted appearance hook follows device changes and page restoration. Reset appearance changes only these four preferences. Display changes do not create game commands or alter other participants' displays.

Device rotation defaults to automatic on phones and tablets. Profiles predating `rotationDefaultsVersion: 1` adopt that default on read, including older saved fixed layouts; the next preference save includes the marker, so later manual choices remain persistent. This changes display preferences only, and retains installation identity, themes, player flips and saved game records.

## Game model

Schema version 1 stores ordered player IDs, player maps, individual commander records, `damageReceived[recipientId][commanderId]`, marker holders, turn/timer state, history, and reversible patches. Combat damage plus optional life loss is one atomic action; a correction changes only damage. Partner damage and casts remain separate. The reducer accepts explicit timestamps, IDs, and random results and does not import React, storage, or network code.

Damage sources and corrections exclude commanders owned by the receiving player. The shared reducer rejects both `damage` and `damageSet` for that pairing before changing damage or life, in local games and authoritative rooms. Older saves remain readable and retain their stored records; self-damage entries do not contribute to displayed damage totals or warnings. Commander tax still uses the player's own commanders.

Numbers are bounded safe integers: life −999,999 to 999,999 and nonnegative trackers up to 999,999. Defaults of 10 poison and 21 damage from one commander are warnings, not automatic elimination. Manual restore is required after elimination. First-player candidates exclude eliminated players. Rematches reset play values with a new match ID while preserving seat/commander identities and configuration.

Local history contains at most 200 gameplay events and 60 undo groups; dice have a separate bounded history. Each hold increment commits normally, with adjacent actions sharing an undo group. Markers and turn highlights remain visible when a holder is eliminated. The interface compares consecutive confirmed snapshots of one match: a newly eliminated player gets a brief, non-blocking notice, and when exactly one player remains standing in a game of two or more, a winner dialog offers the host's ordinary rematch and end commands. Both are presentation only, appear on every device from the same confirmed state, stay silent for a first snapshot or a different match, and are removed by timers rather than animation so they also work with motion off. Shared undo additionally checks the room revision and eligible actor; administrative changes form a barrier to undoing or grouping earlier actions.

Random integers use rejection sampling over cryptographic bytes. Shared rolls are chosen and persisted by the server; animation reads the recorded result. The timer derives from start/pause timestamps. Room clients estimate server clock offset at HTTP request midpoint and refresh it on reconnection/session renewal.

`src/client/dice/` constructs convex 3D dice meshes and projects shaded faces into a full-screen Canvas2D overlay above the board. `motion.ts` throws each die as a rigid body at 240 Hz and records the flight at 120 Hz: gravity, corner impacts with restitution, Coulomb friction that couples spin with travel, and rolling resistance from the mat, until the solid lies still on a face by itself. The recorded result is then read the way a real die is: whichever face ends on top carries the stored value, which is valid because exchanging or turning faces maps each solid onto itself (a d4 presents the face it lies on). Turning the whole throw about the vertical and translating it are physical symmetries of a flat table, so each die also finishes square to the viewer in its own cell without a late attraction toward the grid; only a last fraction of a degree is eased away. A few seeded throws are compared so dice arrive from the players' side and settle within about 2.3 seconds, and a throw that fails to settle is never kept. Dice do not collide with each other. These motions are visual only; their seed never chooses game results. The final render stays static, and reduced motion uses the landed pose directly. Each tied d20 round animates in order, and winner text/scores are mounted only after the final round. The result overlay supports browser Back and dismisses to the board. Percentile rolls display paired d10s. This adds no runtime dependency or external assets.

The landed pose uses exactly zero Euler rotation, showing the recorded face head on with upright lettering and centered asymmetric d10 faces. `rounded.ts` builds a closed surface from inset planar faces, cylindrical edge fillets and spherical corner caps, with lower detail for small dice. `ivory.ts` renders warm ivory for table rolls and resin pigments for player rolls, with normal-based lighting, quiet grain, smooth bevel highlights and recessed ink numbers. The coin is constructed directly as a 32-segment cylinder, with a metallic face, milled rim and contrasting lettering. Browser checks inspect recorded values and actual canvas text transforms, including percentile dice and the coin.

Audio is synthesized locally. Roll gestures unlock/resume the AudioContext before asynchronous persistence; the dice presentation schedules one knock for each simulated strike on the table in a roll/tie round, louder for harder hits, merging corners that land together and keeping the hardest 28. Reduced motion uses one short impact, replay stays silent, and dismissing or muting cancels pending sound. Settings preview the sound on enable and provide a Test dice sound button. Resuming is awaited and failures remain nonfatal; see [AudioContext.resume](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/resume). Device mute, routing and physical speakers remain outside browser automation.

`settings.turnTracking` defaults to false, including when parsing older schema-v1 games. Its host-controlled command is undoable. A first-player roll does not change the turn; confirming it does when tracking is enabled. Legacy counter/marker data remains readable after removal of the Extra trackers UI.

## Local durability

IndexedDB version 1 stores records for the profile, active game, previous checkpoint, ten archives, room previews, and pending room envelopes. Each gameplay write compares the committed game ID/revision inside a read/write transaction, writes the checkpoint and new state together, and renews an 18-second editor lease. A six-second foreground lease refresh and BroadcastChannel improve feedback between tabs; transaction comparisons protect correctness even without channel delivery.

An additional bounded `unfinished` record preserves local games when switching tables. Resume reads the freshest saved version and archives the outgoing table in the same transaction, retaining match ID/revision, damage, names and history. Ended games and rematched predecessors are excluded. A read-only foreground tab checks for an expired lease every six seconds and acquires it transactionally; an active lease still requires explicit takeover.

`endedAt` is a nullable timestamp with a backward-compatible default. Ending stores a separate bounded `standby` snapshot in the same IndexedDB transaction as the game. Home lists ended games until `endedAt + 24 hours`. Reopen checks the deadline and editor lease and saves the outgoing game in a single transaction; it retains the original identity and scores and leaves the timer paused. End/reopen participate in normal history and undo, with expiry also enforced when undo would reopen an ended game. Confirmed active-to-ended transitions return the interface home; merely viewing a finished game does not navigate away again.

The UI previews local actions immediately and displays saving status until the serialized write completes. A stale tab cannot overwrite another tab; explicit takeover makes the former editor read-only. A failed write rolls back the preview and presents an error. Unavailable storage uses a clearly labeled memory fallback. Invalid/future data is preserved, with recovery export, checkpoint restore, or explicit fresh-start controls. Imports validate size (2 MB), schema, integer bounds, and references before replacement. Game exports omit the profile, local installation ID, room credentials, and cookies.

The board selects visible seat primitives so unrelated seat changes do not rerender every tile. Pointer holds are independent and are canceled on lost capture, cancel, release, overlays, navigation, backgrounding, and connection loss. Other controls preserve browser scrolling and zoom.

`profile.tableLayout` is a local display preference; older profiles default to `upright`. `shared` rotates the far row by 180 degrees and enlarges the life controls. Landscape uses two rows, spanning odd player counts evenly; compact layouts with more than four seats may scroll to preserve touch target sizes. Per-seat rotation overrides are honored, and choosing a preset clears those overrides. Neither layout selection nor phone rotation changes game state, room permissions, or another phone's view; My seat stays upright.

## Room authority and synchronization

Sessions use random 256-bit opaque credentials in persistent HttpOnly, SameSite=Lax, Path=/ cookies without a Domain attribute. Only credential hashes are stored in SQLite. HTTPS sets Secure; HTTP requires deliberate configuration. The cookie and server expiry renew together through HTTP on reconnect/foreground and every 15 minutes during active play. Expired authority requires an explicit new join/create action; it is never resurrected as the old member.

An invitation code admits a pending participant to a limited lobby. The host approves a requested seat transactionally; a partial unique database index ensures one approved member per seat. Replacing someone revokes their membership first. Removing a member revokes active sockets. Host transfer preserves seat assignment. Presence is transient and separate from elimination and permissions. Each approved member can view the full table but can change only their assigned player and commanders. Host status grants room administration and shared marker, turn, timer, tracker-setting, end, reopen, and rematch controls; it never grants another player’s life or profile edits. Group life changes are local-only. Legacy shared-edit policy values are ignored, and enabling the policy is rejected. Undo requires the original actor and current ownership of every affected player or commander; the host can also undo their own table-control actions.

Seat requests may carry a validated `profile` with the player's name and optional one/two commander labels. These choices are stored in `members.seat_profile`, survive reconnects/server restarts, and are shown to the requester and host while approval is pending. The limited lobby also receives a `commanderEnabled` flag, without a game snapshot. Guests can update their request; competing/stale approvals still use the existing revision and receipt checks. Approval applies the requested profile and membership in one transaction, clears the pending profile, and records the seat setup in game history. It preserves seat IDs, existing commander IDs, life, damage, casts, and timer; a partner may be added or an unused second commander removed. Removing a commander with recorded damage or casts is rejected without partial membership/game changes. Leaving commander fields blank preserves the seat's labels. Player and commander editing during play is limited to the assigned player, including for the host.

`GET /api/rooms` reads an existing authenticated cookie and lists up to ten unfinished or recently ended, unexpired rooms belonging to that guest. Ended rooms appear for approved members during the 24-hour recovery window, with a host-only reopen capability. It excludes revoked memberships and returns display metadata without invitation codes, credentials, or game snapshots. Home combines these summaries with local games and keeps cached room references for outages. A fresh local player never needs a guest session. Resume reauthenticates against the room controller before enabling input; reopening waits for the socket's ready frame before submitting the ordinary durable command. Server authorization, revisions, expiry and receipt deduplication apply to reopen exactly as to other host actions.

Commands carry protocol version, room ID, match ID, stable operation ID, base room revision, and a strict command payload. Actor and role come exclusively from the session. Every command uses the same validation/authorization path over HTTP and WebSocket:

1. Authenticate, validate the envelope, and look up its actor/operation receipt before mutable role or match checks.
2. Return the original receipt for an identical retry. A revoked actor receives no new private snapshot. Reusing an operation ID with a different payload fails.
3. For a new operation, check current membership and action permissions. Relative deltas apply to the current state; absolute/administrative actions require the current revision.
4. Commit the new game, monotonic room revision, event, and receipt in one SQLite transaction. Acknowledgement and snapshot broadcasts happen only afterward.

Room revision never resets, even after rematch. Receipts outlive the 200-event visible history and are kept for the current match and the one before it. A rematch discards older ones; the match-ID check already refuses their envelopes, so a late retry is rejected rather than applied twice. Clients ignore older views and refresh after gaps. Pending relative previews rebase on confirmed state; committed snapshots remain separate for exports and outage copies.

An operation envelope is saved locally before sending. An envelope is checked against the shared schema before it is queued. An acknowledgement removes that exact ID. Exact life, damage and cast forms await the receipt before clearing a draft. A rejection or uncertain result keeps the entered correction visible. Requests have a 10-second deadline and share a connection-generation abort signal; leaving, hiding or replacing a room cancels obsolete work. Heartbeats respect an existing reconnect attempt and its backoff. After interruption, the client retries recorded IDs, fetches the current state, then enables input. A recorded envelope the server refuses outright (HTTP 400 or 409, which carry no receipt) is set aside with a notice instead of blocking every later reconnect; other failures are retried with backoff. A socket error while changes are unconfirmed triggers the same reconciliation. Disconnects reject new input, cancel holds, and do not intentionally queue unsent edits. Connection generations prevent delayed saves from sending on a replacement room/socket. If authority is lost, pending action records remain readable for reconciliation. Copying the confirmed state into local play creates an independent game and never merges it automatically.

The server sends current room snapshots, including bounded history. It validates and caches each persisted game once per room state (up to 128 rooms), reuses encoded common game data, and constructs recipient-specific membership/permission overlays. Room/session/member socket indexes target fanout and presence checks. Broadcasts coalesce over 16 ms; an actor who already received the same revision and presence in its acknowledgement receives no duplicate state frame. It uses one subscription per socket, heartbeat checks, jittered reconnect backoff, a 16 KB message/command limit, rate limits, and a 1 MB outbound socket buffer limit. HTTP and WebSocket commands share session (60 burst, 30/second) and room (160 burst, 80/second) budgets; another tab cannot obtain another command allowance. Socket admission caps default to 512 global, 64 per room and 12 per guest session. HTTP and WebSocket origins must match `PUBLIC_ORIGIN`; state-changing HTTP and WS commands have CSRF checks. Session bootstrap requires a protocol header. Card lookup routes need no session; besides their own limits they share one budget of 100 requests a minute per client, below the pace of the single upstream queue, so one client cannot keep that queue full. Payloads, cookies, tokens, and invitation URLs are not logged.

## Database and retention

SQLite uses WAL, foreign keys, FULL synchronization, a five-second busy timeout, and transactional schema migrations. Tables hold sessions, rooms, members, operation receipts, bounded events, and up to ten final match snapshots. The first migration creates schema version 1; version 2 adds nullable `members.seat_profile`. The current maintenance build adds schema 3: a durable room retry floor, tracked receipt counts, receipt base revisions and retention indexes. Migration preserves existing games, memberships and receipt results. A newer database is rejected by an older application; rolling back this build requires its verified schema-2 pre-update backup.

Rooms expire 30 days after their last committed gameplay/administrative activity by default. Sessions have a configurable rolling 90-day lifetime. A minute cleanup interval removes expired records and notifies affected sockets; presence and heartbeats do not extend room retention. A session that belongs to no room is removed a day after its last renewal. When cleanup removes a host's expired session, the longest-seated approved member becomes host; a room with no approved member keeps its last host ID until it expires. A lost host credential has no invitation-code recovery mechanism.

Run one server process against one database on local storage. Scaling across machines or using a network filesystem requires a different design. Browser-local games and preferences are not included in the server volume.

## Production and PWA

Fastify serves assets and the API from one origin. Hashed assets are immutable; HTML and the service worker revalidate. Private API responses use `no-store`, and the service worker never falls back to the app shell for `/api/`. Only application assets are precached, including local fonts/icons. An update prompts for confirmation and waits for pending saves rather than reloading mid-game.

HTTP LAN use includes an ID fallback based on `crypto.getRandomValues()` when `randomUUID()` is unavailable. Wake lock, vibration, fullscreen, sound, installation, and offline reopening are optional enhancements; normal browser-tab play does not require them.

## Optional commander artwork

A commander may carry validated public Scryfall metadata (`id`, front-face `name`, `imageUrl`, `scryfallUrl`, `artist`). Setup and pending seat profiles carry aligned nullable card arrays for one or two commanders. The existing commander-name command saves or clears artwork under the same assigned-seat permissions, and the normal game reducer, history, exports, rematches and room snapshots preserve it. A manual rename clears the previous card so an old picture cannot silently follow a different commander.

The optional read-only `/api/cards/suggest` and `/api/cards/resolve` endpoints need no guest session. They share one bounded server cache and serialized upstream queue (550ms request spacing, 24-hour entries, a maximum of 12 pending keys and 256 cached results). Response sizes, queue waits and network time are bounded. Scryfall rate-limit responses pause all new upstream work for at least 30 seconds. User-supplied URLs are parsed into fixed Scryfall API paths; they are never fetched as arbitrary destinations. Names, artwork URLs and card links are validated before storage, including imported saves.

Artwork images come only from the Scryfall image host allowed by the production CSP. A separate CacheFirst service-worker cache keeps at most 64 successful CORS art-crop responses for 30 days and can purge on quota pressure; private game APIs still use no-store and are never cached. Metadata stays in the game, so cached art can display during offline play. Missing images fall back to the existing panel, and an online event retries a failed image once. Card lookup has no effect on life totals or game availability.

## Bounded retries, browser snapshots and operations

Each room keeps at most `ROOM_RECEIPT_LIMIT` receipts (20,000 by default). Ordinary retention advances a durable revision floor after the configured `RETRY_REVISION_WINDOW` (10,000 revisions), checked every 128 revisions. Reaching the receipt cap also advances the room revision and retry floor atomically, retains the newest half of receipts, and preserves the last safe undo. Receipt lookup runs before this floor check: retained acknowledgements still return their original result. An unknown envelope behind the floor is refused without applying it. The client preserves the original envelope/operation ID during reconciliation and reports an expired retry for manual review. Repeated rejected actions therefore cannot grow a room’s receipt table without bound. Rematches retain the previous-match retry behavior within these limits.

A browser persists a room only when its room/game revision or durable membership metadata changes. Live presence and server clock samples still update in memory. Room cleanup retains the ten recent references, the active room and any room with pending or unreadable action records. Resolving an old room’s pending records makes its snapshot eligible for subsequent cleanup.

Optional sheets, card tools, room/QR tools and dice are separate lazy chunks. Four WOFF2 font faces replace the redundant WOFF fallbacks and unused weights. The service worker precaches every application chunk so these tools can still open for the first time during an origin outage. Dice start at a quality tier appropriate to their count and reduce detail/DPR if drawing repeatedly exceeds 24 ms. Full quality keeps rounded fillets and resin grain; crowded/slow throws use simpler closed solids, flat lighting and cached label metrics. Recorded values, simulation tracks, completion and reduced-motion behavior remain identical.

Home places quick local play, room creation and joining together on the first mobile screen. Settings offer four coordinated table looks above the custom palette/accent/finish controls. Commander-art controls use a dark surface and neutral light icons in either appearance mode; the scrim concentrates behind text while leaving more artwork visible. Artwork framing is a bounded, browser-local `artPositions` preference keyed by card ID. It neither changes shared commands nor adds fields to the strict game protocol.

`operations.ts` maintains private numeric request/error/command counts, rolling request and event-loop p95, socket/room counts, database/WAL sizes, disk availability and backup freshness. It writes `/data/operations.json` atomically with mode 0600 every 30 seconds. Failure logs contain fixed event names, status, route templates, generated request IDs and sanitized error categories. They exclude tokens, invitation URLs, player names and command payloads; no public diagnostics endpoint is added.

The server creates a verified online backup at startup when overdue and every 24 hours thereafter. Each copy uses SQLite’s backup API, switches the copy to DELETE journaling to make it self-contained, checks database integrity and foreign keys, and records a SHA-256 checksum. It retains the newest 14 scheduled copies, leaving manually named backups alone. An optional `BACKUP_COPY_DIR` receives a separately verified copy; operators must mount a separate disk or remote filesystem for actual off-host protection. The default remains the existing local volume. Shutdown awaits an in-progress backup before closing SQLite.
